## 为什么可能与旧实验不同

### 已确认：与修改前仓库默认配置的差异

`0df36c8` 的单卡包装脚本默认 batch64、chunk8、expert chunk64。
当前实际运行是 EV batch32、VR batch40、chunk120、expert chunk128。
其余模型/损失配置在相同任务下保持一致；代码实现层的差异见三个提交。

- 原默认每轮3200条轨迹、每次优化器更新16个实例。
- 当前 EV 每轮1600条轨迹、每次更新8个实例；VR 为2000条轨迹和10个实例。
- 都是每轮5次 PPO passes、4个 minibatches，即20次更新尝试。

因此，同样 epoch 下的采样量及minibatch方差已不同；每条轨迹仍参与5次PPO passes。
较大的 chunk 主要改变峰值显存及执行分块，不会增加独立实例或优化器步数。
浮点累计顺序仍可能不同，不保证训练轨迹逐位一致。

### 已确认：值得单独消融的实现变化

1. **SL-PPO AMP 一致性**：修改前，路线概率比预计算在 AMP 外进行，梯度前向在 AMP 内进行。
   现在二者一致，可能改变路线权重及 clipping 的判断。这是两种任务都应优先排查的因素。
2. **AGDA 非活动资源输入**：VRPTW 中，旧电池 margin/feasibility 通道在正常输入下也可能为1，现在按资源标志清零。
   这会改变学习后的决策，不只是在异常数据上生效。EVRPTW 的所有资源有效且输入有限时，此修复通常不改变这些通道。
3. **计算优化与数值路径**：单 query 与全 token query 的数学目标相同，但投影/attention内核形状可能变化。
   CPU 输出与梯度通过容差测试；不能据此断言跨 GPU 的 FP16 输出逐位相同。
4. **无效步骤与资源值屏蔽**：修复 NaN/Inf padding 和低精度累计；是否解释真实数据上的质量差异，需要同配置对照。

### 尚未确认：2080Ti 历史运行

尚未定位到用户所指旧实验的 config/manifest，不能把仓库某个默认脚本当作其实际配置。
`scripts/paper_2080ti_runs/` 中可见的旧默认包括 seed3009、batch64、SL-PPO4、PPO第100轮权重初始化、
weighted priority sampling、horizon90、每20轮验证；现有包装脚本覆盖Cus15/Cus50，并非这次Cus100的确切历史证据。
这些默认与当前实验存在多项差异，但仍需旧运行文件逐项核对。

## 建议的最小归因实验

| 对照 | 固定什么 | 能回答什么 |
| --- | --- | --- |
| 当前已排队 graph / current | 同任务、数据校验和、seed、batch、损失与验证协议 | 在当前修复代码下，编码器的贡献 |
| 基线 / 仅 AGDA 修复 / 仅 SLPPO 修复 / 两项修复 | 同一个显式配置、GPU和软件环境；统一启动适配 | 两组实现修改各自的贡献 |
| 同一修复版本，小batch / batch64 | 模型、seed、其他训练与验证规则 | batch及采样预算的影响 |

比较实现时可以用前两条独立提交进行 cherry-pick；所有实验使用相同的单卡启动修复或显式 `--device cuda:0`。
不要让基线自动退回旧的 batch64/chunk8 默认值。资源不足时显式缩小 chunk，保持目标batch及其他协议一致。
同时报告按 epoch、采样实例数、优化器步数和实际耗时的曲线；最终结论需要多个配对seed。
若要判断硬件贡献，再固定 checkpoint、输入、精度和软件配置测量两种 GPU；显存占用本身不是解质量证据。
本次只留档方案，没有启动这些额外消融。
